# パターン一覧

`scan.mjs` が検出するパターンと、検出できないが目で見て直すパターンをまとめる。
各項目のIDは `scan.mjs` の出力と同じ。

判定の重さは2段階ある。
要修正は誤検出が少なく、見つけたら直すもの。
助言は文脈しだいで、残す理由があれば残してよいもの。

## 目次

1. 言い回し（scan.mjs が検出する）
2. 構成（scan.mjs が検出する。文書とPR本文だけ）
3. 目で見て直すもの（scan.mjs では検出できない）
4. 直さないもの

## 1. 言い回し

### closing-cliche（要修正）

「いかがでしたか」「参考になれば幸いです」のような定型の締め。
締めの一文ごと削る。
読み手が次にすることがあるなら、それを書いて終える。

- 元: いかがでしたか？この記事が参考になれば幸いです。
- 直し: （削る）

### sycophancy（要修正）

「素晴らしい質問ですね」のように相手を持ち上げる定型句。削って本題から書く。

### double-dash（要修正）

全角ダッシュ（——、―、—）で文をつなぐ書き方。
英語の em dash を日本語に持ち込んだもので、日本語の文章では目立つ。
読点で続けるか、文を分ける。
括弧やコロンに逃がさない。

- 元: キャッシュの無効化——これは最も難しい問題の一つです。
- 直し: いちばん難しいのはキャッシュの無効化です。

### preface（助言）

「本記事では〜について解説します」のような前置き。
読み手に何も伝えないので、結論から書き始める。
ただし、長い手順書などで対象範囲を示す一文は残してよい。

### koto-ga-dekiru（助言、2回以上で指摘）

「〜することができます」は「〜できます」で足りる。
可能だと強調したいときだけ残す。

### hedge-cliche（助言）

「〜と言えるでしょう」「〜ではないでしょうか」のように確信をぼかす定型句。
言い切れるなら言い切る。
推定なら「〜と見ている」「〜だろう」と、推定であることが分かる形にする。
確信の度合いそのものは変えない。

- 元: このツールを使用することで、作業効率を大幅に向上させることができると言えるでしょう。
- 直し: このツールを使うと、作業の効率は大きく上がるだろう。

### stock-words（助言、3回以上で指摘）

「重要です」「さまざまな」「〜において」「シームレス」「包括的」「大幅に向上」などの意味の薄い語。
何がどう重要か、どの場面か、どれだけ上がったかを書けるなら書く。
素材に具体的な中身がなければ、語を削るだけにして中身を作らない。

### not-but（助言、3回以上で指摘）

「〜ではなく、〜」の多用。
誰も言っていない思い込みを先回りして打ち消している文が多い。
読み手が実際に誤解しそうな箇所だけに残す。

### orphan-mazu（要修正。コードのコメントでは助言）

文頭の「まず、」のうち、同じ節の中に「次に」「最後に」などが続かず、順序を示していないもの。
書き出しの口癖として付いていることが多い。
「まず、」を外して、そのまま書き始める。
「まずはこちらをご覧ください」のような「まずは」は対象外。

- 元: このPRはよくまとまっていると思いました。
  まず、エラー処理が一か所にまとまっている点で読みやすいと評価できます。
- 直し: このPRはよくまとまっていると思いました。
  エラー処理が一か所にまとまっていて読みやすいです。

評価や所感を複数並べたいなら、「まず、」で始めずに番号付きの見出しや箇条書きにする。

### spoken-verb（助言）

処理や効果を、話し言葉の動詞で書いたもの。
2種類あり、どちらも柔らかく読めるが、何が起きるのかが読み手に伝わらない。

- 口語の比喩: 「効く」「刺さる」「〜が肝」
- 意味の広い和語の基本動詞: 「見る」「拾う」「抑える」「沿わせる」「回す」「叩く」「走る」。
  「見る」は、目を通すだけなのか、確かめたのか、判断したのかを区別しない。

書き言葉で、何が起きるかを特定できる語にする。
多くは「チェックする」「検出する」「抑制する」「適用する」「実行する」のような漢語の動詞になる。
ただし、何でも漢語にすると硬くなるので、書き換えるのは処理や効果を述べる箇所だけにする。
「薬が効く」「画面を見る」のように文字どおりの意味なら残す。

- 元: ここでキャッシュが効くので速くなります。
- 直し: ここでキャッシュを使うので、2回目からの応答が速くなります。
- 元: 書いている最中からルールに沿わせます。改行も見ます。チャットの返信はルールだけで抑えます。
- 直し: 書いている最中からルールを適用します。改行もチェックします。チャットの返信はルールだけで抑制します。

### conclusion-first-cliche（助言）

「結論から言うと」「一言で言えば」。予告せずに結論そのものを書く。

### exclamation（助言、3回以上で指摘）、emoji（助言）

「！」や絵文字で飾る書き方。
相手がそういう書き方をしている場面や、リポジトリの慣習（gitmoji など）なら合わせてよい。

### fullwidth-alnum（助言）

全角の英数字。半角にそろえる。

## 2. 構成

### bold-label-bullets（要修正、3行以上で指摘）

「- **ラベル**: 説明」の箇条書きが続く形。
AIの文章でいちばん目立つ型。
ラベルを外して説明だけにするか、項目どうしに関係があるなら文でつなぐ。

- 元:
  - **高速化**: レスポンス時間を短縮します。
  - **負荷軽減**: サーバーの負荷を軽減します。
- 直し: 応答が速くなり、サーバーの負荷も下がる。

### bold-density（要修正 / 助言）

太字の多さ。
日本語1000字あたり8か所を超えると要修正、4か所を超えると助言。
文書全体で本当に目立たせたい1〜2か所に絞る。

### summary-section（助言）

最後の「まとめ」「おわりに」の節。
本文の繰り返しなら削る。
調査レポートで「次に何をするか」を書いているなら残す。

### heading-density（助言）

本文の量に比べて見出しが多い。
見出しは読み手が探す場所にだけ付ける。
数行ごとの見出しは外して段落にする。

### bullet-heavy（助言）

本文のほとんどが箇条書き。
因果や経緯（「だから」「しかし」でつながる内容）は文で書く。
宿題や手順のように独立した項目は箇条書きのままでよい。

### long-sentence（助言）、long-paragraph（助言）

90字を超える文と、300字を超える段落。
AIは説明を足しすぎる傾向があり、長さはその目安になる。
読み手が判断や作業に要る分だけに削るか、主張ごとに文を分ける。
モックアップやUIの説明文では、画面を見れば分かることを書いていないか確かめる。
長さそのものが悪いわけではないので、条件や例外をまとめた文は残してよい。
レビューや仕様のように正確さが要る文書では、指摘や条件の数を減らして短くしない。
削るのは前置きと繰り返しだけにする。

### line-break（助言）、long-block（助言）

改行のない文章は、画面で読むと詰まって見える。
逆に、すべての句点で改行すると箇条書きのように見え、文どうしのつながりが見えにくくなる。
チャットの返信、箇条書きの各項目、ドキュメント、メール、PR、コミットメッセージのどれにも当てる。コードのコメントは対象外。

同じことを述べる2〜3文は1行に続ける。
1行が80字を超えそうなとき、4文目に入るとき、話が一歩進むときに句点で改行する。
同じ話題の文は空行を挟まずに続け、話題が変わるところで空行を1行入れる。空行のないまとまりは5行までにする。
読点の位置など文の途中では改行しない。

- 元（改行がない）: 先日の件ですが、見積もりの再提出は来週水曜でも問題ないとのことでした。金額は前回と同じです。納期だけ1週間後ろにずらします。担当は引き続き山田さんです。
- 元（すべての句点で改行）:
  先日の件ですが、見積もりの再提出は来週水曜でも問題ないとのことでした。
  金額は前回と同じです。
  納期だけ1週間後ろにずらします。
  担当は引き続き山田さんです。
- 直し:
  先日の件ですが、見積もりの再提出は来週水曜でも問題ないとのことでした。
  金額は前回と同じで、納期だけ1週間後ろにずらします。担当は引き続き山田さんです。

箇条書きの項目の中で改行するときは、続きの行を項目の本文の位置にそろえて字下げする。

```
1. 外部の決済APIを呼んでいる場合、ロールバックしても課金は戻りません。
   在庫を先に減らすか、失敗時に返金する処理が要ります。
```

Markdown の表示によっては、段落の中の改行が空白として表示されることがある。それでもソースは読みやすくなる。

### monotone-length（助言）、same-ending（助言）

文の長さがそろいすぎている、同じ文末が4回以上続く。
内容に合わせて、短い文と長い文を混ぜる。
型を崩すために疑問形や体言止めを足すのは逆効果。

## 3. 目で見て直すもの

`scan.mjs` では検出できないので、直すときは本文を通して読んで確かめる。

- 元にない数の枠組み（「理由は3つあります」）や、何でも3つに揃える並べ方
- 同じ書き出しや同じ段落の型が3回以上続くこと
- 中身のないつなぎの文（「以下で詳しく見ていきます」「それでは早速」）
- 見出しを本文の1文目で言い直すだけの書き出し
- 書き手の体験や評価を装った一般論（「これには何度も助けられました」）
- 「〜という形で進めていく予定です」のような、字数だけ増やす言い回し
- 何の話かが後になってから分かる列挙（列挙のあとに「〜といった点に注意しました」）

## 4. 直さないもの

- 元の文書にある事実、数値、人名、日付、条件。
  誤りに見えても書き換えず、ユーザーに伝える
- 確信の度合い。「かもしれない」を断定に変えない。逆も同じ
- です・ます体とである体、敬語の度合い。頼まれない限り変えない
- 意味の通じる言葉の好みによる言い換え
- 引用、コード、URL、固有名詞、製品名に含まれる語（「多角的レビュー機能」の「多角的」など）
- 書き手の癖（話し言葉の引用、矢印や略記、改行で区切る書き方）。
  読みにくくない限り残す
